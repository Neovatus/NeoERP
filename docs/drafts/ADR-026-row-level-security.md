## Summary (plain English)
**Turn on Postgres row-level security (RLS) for the services that hold company money and people data: Accounts now, Payroll and HR in their rebuilds from their first migration, and the reporting store (already decided in ADR-023).** Leave org-, user-, audit- and auth-service on application checks plus route tests for now; they are platform services whose normal reads cross companies by design. Each transaction tells the database its one company with `set_config('neoerp.company_id', …, true)` (the same as `SET LOCAL`). A shared aspect does this from the `CompanyTenantScope` that ADR-012 already forces into every tenant repository call. No setting means no rows. The app role never owns tables and never has `BYPASSRLS`. Cross-company machine jobs and Super Admin platform reads get narrow, named policies on only the tables they need. Every flag is read through an owner function that turns the pooled-connection `''` into NULL. This is a safety net under ADR-012, not a replacement.

### Background
| Idea | Plain English |
|---|---|
| RLS | Postgres adds a hidden `WHERE company_id = …` to every query on a table, whatever the app wrote. |
| Policy | The rule a table uses (`USING` for reads, `WITH CHECK` for writes). |
| `ENABLE` / `FORCE` | `ENABLE` turns the rules on for other roles; `FORCE` also holds the table owner to them. Superusers always skip RLS. |
| `BYPASSRLS` | A role attribute that skips every policy. The app must never have it. |
| `SET LOCAL` / `set_config(…, true)` | A value that lasts only until the transaction ends, so a pooled connection carries nothing to the next borrower. |
| Owner vs runtime role | Flyway migrates as the owner; the service connects as a role that owns nothing (P-5). Accounts already works this way. |

## 2. Options
| | A. No RLS, stronger tests | B. RLS on Accounts + rebuilt Payroll (and HR, reporting) — **recommended** | C. RLS on every company table in all services |
|---|---|---|---|
| What | Keep ADR-012 only; add L17 cross-company route tests, two-company adapter tests, skip-check (P-16) | Policies on every company-bound table in accounts, payroll v2, hr v2, reporting store | B plus org, user, audit (`org_id`) |
| Build cost | S (route-test generator already planned, L17) | M for Accounts (97 tables, one aspect, jobs); ~0 extra for Payroll/HR if done in their first migration | L: user and org read across companies on almost every auth path; needs many platform policies |
| Risk it removes | A wrong route; not a wrong SQL in a covered route that tests miss | A missing or wrong `company_id` predicate on money and people data, including native SQL and new reports | Same, plus IAM/org rows |
| New risk | None | Missing setting → an error on company-only tables, an empty result only on the few tables that also have a system or platform policy (M4, Fable, 2026-11-21); job paths need care | High chance of false denials on auth paths; outages look like permission bugs |
| Performance | none | One extra round trip per transaction (~0.1–0.3 ms); predicate matches company-leading indexes (ADR-024 §1) | Same, but on the hot auth path of every request |
| Flyway | none | Each new company table ships `ENABLE`/`FORCE` + policy; a catalog test fails a table without it | Same, in 3 more services |
| Testcontainers | more tests | RLS suite connects as the runtime role; later the fixture's app connection too | Same, in every service |
| Seeds | none | Seeds run as superuser locally; unaffected | Same |
| Reporting/read models | app-only | Matches ADR-023 ("RLS from day one", group view = one query per company) | Same |
| Platform jobs, Super Admin | unchanged | Named per-table system and platform policies (§3.5–3.6) | Many more such policies (IAM, org, audit) |
| Go-live ERP-Q4 | Does not meet it | Meets it for money and personnel data | Meets it fully, latest |

Option A is rejected as the end state: C3 asks for a second layer, and a test only proves the paths someone wrote a test for. Its tests are still required under B (ADR-012 acceptance 4, L17). Option C is rejected now: org and IAM are where "which companies can this person reach" is computed, so their legitimate reads cross companies; RLS there gives little and costs the most. audit-service is the exception: it gets its own dated step (R7, D2), because it stores the same audit payloads Accounts protects.

## 3. Decision (mechanism for option B)
Mechanism items are M1–M9. Jabran's decisions in §7 keep the numbers D1–D11.

**M1. Scope.** RLS on every company-bound table of accounts-service now; of payroll-service and hr-service from their rebuild's first migration; of the ADR-023 reporting store from its first migration. **Every later business service (Inventory, Purchase, Sales) ships RLS in its first migration too (Fable, 2026-11-21).** audit-service gets RLS on its company rows in R7 (D2). Accounts `audit_outbox` is company data too (each company's `payload_text` and `reason` under a nullable `org_id`, `V6__a0_baseline.sql:327-340`): it gets RLS keyed on `org_id` (M6, D11). Platform reference tables (no company column) get no RLS. Today the runtime role has full data rights on every table (`accounts-runtime-role.psql:36,40`); R2 revokes `INSERT, UPDATE, DELETE` on the reference tables (they are loaded by Flyway only, `TenantRepositoryArchitectureTest.kt:397-401`), and `RuntimeRoleCheck` refuses to start if the role can write one.

**M2. Every flag is read through an owner function with `NULLIF`.** After a pooled connection has once used `SET LOCAL`, a custom setting reads as `''`, not NULL, in every later transaction on that connection. A raw `current_setting(…) IS NOT NULL` test would therefore stay true forever. So no policy reads a setting directly. Five `STABLE` functions, owned by the owner role, each reading `NULLIF(current_setting('<name>', true), '')`:
| Function | Setting | Set by | Type |
|---|---|---|---|
| `neoerp_required_company()` | `neoerp.company_id` | binder, from `CompanyTenantScope` (M3) | `uuid`; **raises an error when no company is set** (Fable, 2026-11-21). Used by the company policy on every table that has no system or platform policy, so a missed bind is an error, not an empty answer (M4). |
| `neoerp_current_company()` | `neoerp.company_id` | binder, from `CompanyTenantScope` (M3) | `uuid`, NULL when unset. Used only on the tables that also carry an M6 system or M7 platform policy. |
| `neoerp_system_job()` | `neoerp.system_job` | `bindSystemJob(name)` (M6) | `text` |
| `neoerp_platform_access()` | `neoerp.platform_access` | `bindPlatform(access)` (M7) | `uuid` (operation id) |
| `neoerp_migration()` | `neoerp.migration` | Flyway init SQL (M5) | `text`, must equal `'on'` |
Every policy names its role in `TO` (the runtime role, or the owner for the migration policy). No policy is `TO PUBLIC`. Session-level settings are forbidden: an architecture test fails on `set_config('neoerp.…', …, false)` or `SET neoerp.` without `LOCAL` in main code. **One named exception (Fable, 2026-11-21):** Flyway's init SQL sets `neoerp.migration` for the migration connection only (M5); the ban test names that one setting. A session-level or hand-written bind anywhere else would leak across pooled connections or be forgotten. The value dies at commit or rollback, before Hikari gets the connection back, and it is safe behind a transaction-mode pooler (ADR-024 D5, **draft, not yet accepted**).

**M3. One company per transaction, from the existing scope.**
- A shared `TenantTransactionBinder` (new, in `shared/tenant-security`) runs `SELECT set_config('neoerp.company_id', :id, true)` on the transaction's connection (`DataSourceUtils`, so JDBC and JPA share it).
- A Spring aspect calls it around every bean that implements a `@TenantOwnedRepository` interface. ADR-012 already guarantees the first argument is `CompanyTenantScope` (`TenantRepositoryArchitectureTest.kt:148-172`), so no per-method code is needed.
- **The marker lives with the connection, not as a plain bound resource.** Spring does not suspend plain bound resources for `REQUIRES_NEW`; it does suspend transaction synchronizations (`DimensionSetJdbcAdapter.kt:125-130` explains and relies on this). So the binder keeps "company X is set on connection C" in a `TransactionSynchronization` registered for the transaction, and checks the current `ConnectionHolder`'s connection against it on every call. A different connection (an inner `REQUIRES_NEW`, as in `ExportSupport.kt:55-69`, `LedgerCheckJob.kt:44,51`, `ScheduledReversalJob.kt:90,95,102`, `FiscalSubmission.kt:49`, and the recurring-journal job) has no marker, so `set_config` runs again on it. When the inner transaction ends, the outer marker resumes with the outer connection, where the setting is still in place.
- **Savepoints:** a rollback to a savepoint undoes a `set_config` made after it, while a synchronization would keep the marker. Main code uses no `NESTED` propagation or explicit savepoint today (only a warning in `DimensionSetRepository.kt:19-22`). An architecture test keeps it that way in RLS services. If one is ever needed, the binder must re-run `set_config` after the savepoint, and §5.4 proves it.
- Same company again in the same transaction and connection: nothing to do. **A different company in the same transaction throws** (no mixing). With no transaction active, the aspect opens one (`REQUIRED`) around that call, so the setting never falls into autocommit.
- **No mixing of bind kinds (Fable, 2026-11-21).** The binder refuses a system-job or platform bind in a transaction that already has a company, and a company bind in a transaction that already has a system-job or platform bind.
- **The aspect runs inside the transaction advice (Fable, 2026-11-21).** It is ordered after Spring's transaction interceptor, so it binds on the connection the method actually uses, including an adapter method that opens its own transaction. 33 Accounts JDBC adapter files use `@Transactional(MANDATORY)` (e.g. `ACC/infrastructure/persistence/jdbc/ArReceiptJdbcAdapter.kt:38`); jobs open `REQUIRES_NEW` in the service and then call adapters (`ACC/application/service/posting/LedgerCheckJob.kt:42-52`). A binder test proves the order (§5.3b).
- **The outbox appends go through the binder too (Fable, 2026-11-21).** The audit append has no scope today (`AuditOutboxRepository.append(record)`, `ACC/infrastructure/persistence/jdbc/AuditOutboxJdbcAdapter.kt:26`, called from `ACC/application/service/audit/AccountsAuditWriter.kt:121`), and the domain-event append, which already takes the scope first (`ACC/application/port/outbound/audit/AuditOutboxRepositories.kt:111-115`), sits on a system repository the aspect does not wrap. Both would work only if a tenant repository happened to run first in the same transaction. R2 moves the company appends to a scope-first `@TenantOwnedRepository` append port, split from the dispatcher's system port, so the aspect binds them. The M7 platform-audit append keeps its own port with `PlatformTenantAccess` first.

**M4. Policies (same shape on every company table).**
```sql
ALTER TABLE accounts.journal_lines ENABLE ROW LEVEL SECURITY;
ALTER TABLE accounts.journal_lines FORCE ROW LEVEL SECURITY;
CREATE POLICY company_isolation ON accounts.journal_lines
  FOR ALL TO neoerp_accounts_app
  USING (company_id = (SELECT neoerp_required_company()))
  WITH CHECK (company_id = (SELECT neoerp_required_company()));
```
Tables that also carry an M6 system or M7 platform policy use `neoerp_current_company()` instead, so a system or platform transaction with no company is not an error there.
The `(SELECT …)` form is evaluated once per query, so the planner still uses `company_id`-leading indexes. HR v2 / Payroll v2 child tables carry their own `company_id NOT NULL` (composite FKs `(company_id, parent_id)`, `docs/drafts/hr-payroll/HR-PAYROLL-LEAD-REVIEW.md:147-148`), so no policy needs a join. Views, if any, are `security_invoker = true`. Triggers and functions stay `SECURITY INVOKER`.
**Missing setting = error, not "all clear" (Fable, 2026-11-21).** On a company-only table, no company → `neoerp_required_company()` raises, so the query fails and shows as `TENANT_SETTING_MISSING` in tests and logs. On the few tables that also have a system or platform policy, no company → NULL → no company row matches: reads return nothing and writes fail `WITH CHECK`; the binder logs a `TENANT_SETTING_MISSING` security event when a write fails this way. "0 rows" from a scheduled job or start-up check is therefore never proof that there was nothing to do: R2 adds a test per scheduled job and start-up check, run as the runtime role with two companies, that asserts work was done in both (§5.7a).

**M5. Roles.**
| Role | Who | Attributes | RLS |
|---|---|---|---|
| `neoerp_<svc>_owner` | Flyway only | owns schema; **not superuser, no `BYPASSRLS`** in hosted stacks | `FORCE` holds it; data migrations set `neoerp.migration = 'on'` through Flyway init SQL, and one policy per table `TO neoerp_<svc>_owner USING (neoerp_migration() = 'on')` |
| `neoerp_<svc>_app` | the service | `NOSUPERUSER NOBYPASSRLS NOINHERIT`, owns nothing (as today) | M4 company policy, plus M6/M7 policies on named tables |
| `neoerp_<svc>_backup` | logical backup and restore only (Fable, 2026-11-21) | read-only, held by no service, its use logged; needs `BYPASSRLS` or `pg_dump` errors on forced tables | none (skips them by its attribute; this is the one role besides the local superuser that may) |
| `neoerp_<svc>_checks` | the scheduled money checks in production, ERP-Q3 (Fable, 2026-11-21) | read-only, held by no service, its use logged; today the script runs as the superuser (`scripts/money-invariants.sh:29`) | one read policy per table it checks, under its own role |
| `neoerp_support` | support access (Fable, 2026-11-21) | read-only where possible, held by no service, time-limited, its use logged | to be designed with the support process before the first customer |
The owner role is **created per service `NOSUPERUSER NOBYPASSRLS` on every hosted stack, never the provider's admin role** (Fable, 2026-11-21; Q2). Provider snapshots are physical copies and are not affected by RLS; logical dumps need the backup role.
**What `FORCE` on the owner does and does not do:** it only guards against accidental use of the owner connection (a wrong datasource user, a script run as owner): such a session sees no company rows. It is not a control against the owner itself, which can `ALTER TABLE … NO FORCE ROW LEVEL SECURITY` or set `neoerp.migration`. The real control is that the service never holds the owner's password at runtime (P-5). `RuntimeRoleCheck` (FAIL outside local/test) also checks that every company-bound table has `relrowsecurity` and `relforcerowsecurity`, and **compares the full set of policies against the expected list**, so a hand-added permissive policy stops the service (Fable, 2026-11-21). Locally the owner is the `neoerp` superuser and skips RLS; that is accepted for dev only.
**Keeping `FORCE` honest (Fable, 2026-11-21):** `FORCE`'s lasting value is that a future view or definer function owned by the owner cannot skip the policies (none exist today). Three rules make the migration-flag path real:
1. **The flag path is tested locally.** It only exists where the owner is not a superuser, so the RLS suite runs Flyway in Testcontainers as a non-superuser owner with the flag set. Otherwise its first proof is on staging.
2. **A data migration without the flag fails.** Without it, a data migration updates 0 rows and still "succeeds"; pack releases already update every company's accounts inside a migration (`ACC/infrastructure/persistence/pack/Pack2026_4.kt:95-118`). A Flyway callback fails the run when `neoerp_migration()` is not `'on'` on the migration connection (once the M2 functions exist).
3. **A missing app role fails the migration.** Today's migrations skip their grants when the role is absent (`IF EXISTS (SELECT 1 FROM pg_roles …)`, e.g. `V69__a4_journal_import.sql:130`). An RLS migration that skipped the same way would leave a table with no wall or with no policy. RLS migrations raise instead, and role creation becomes a step before Flyway on every stack and test fixture.

**M6. Cross-company machine jobs.** Two steps, never one wide query over company data:
1. **Claim or select** on the system tables already on the allowlist (export, SIE and journal-import queues, bank notices, evidence cleanup, opening-import expiry, audit and domain outboxes, org event inbox, and `accounts_setups` for the LIVE company list). Postgres allows one command per policy, so each table gets **one policy per command it needs**, all `TO neoerp_accounts_app` and **naming the jobs allowed on that table** (Fable, 2026-11-21), for example `USING (neoerp_system_job() = 'export-worker')` or `IN ('audit-dispatcher')`, not only "is set", so one job's bind cannot read another job's tables: `FOR SELECT` and `FOR UPDATE` on the queues and outboxes; `FOR DELETE` only where the job deletes (evidence cleanup, opening-import expiry, retention); `FOR SELECT` only on `accounts_setups`. These policies exist **only on those tables**, so a wrong system bind cannot reach `journal_lines`. The catalog test (§5.5) lists every allowed (table, command, job) entry and fails on any other.
   **Company selection reads `accounts_setups` only (Fable, 2026-11-21).** A job whose company list needs a condition on a business table (an ACTIVE template, a pending schedule) does not get a system policy on that business table: it takes every company from `accounts_setups` and checks the condition per company in step 2. All-company alert gauges are summed per company the same way.
2. **Work** for each claimed row in its own transaction under `SystemTenantScopes.forCompany(row.companyId, …)`, which binds the company as in M3. The ledger check is already shaped this way (`LedgerCheckJob.kt:55-77`); its port changes from `companyId: UUID` to the scope.
**The inventory comes first (Fable, 2026-11-21).** Before the R2/R3 migration, a written inventory lists every SQL path not behind a tenant repository. Today it holds the 11 allowlisted system repositories and the six paths of §1.3. Each of the six is either added to the allowed (table, command, job) list or reshaped in R2:
- `RecurringJobCompanies`, `ReversalScheduleCompanies`: reshaped to the company-selection rule above; the two recurring gauges become per-company sums.
- `ApprovalProposalQueue`, `PayeeVerificationJobs`: become allowlisted system repositories with named per-table policies on their queue tables, or select companies from `accounts_setups` and work per company; the R2 brief picks one per path.
- `BankDetailsReencryption`, `BankKeyChecks`: today each reads several companies in one transaction (`BankDetailsReencryption.kt:24-83`, `BankKeyChecks.kt:13-66`); both loop over every company in `accounts_setups`, whatever its state, so no ciphertext is skipped, one company per transaction; `remaining()` is the sum of the per-company counts. `bank_key_checks` itself has no company column and stays without RLS.
The arch test's name filter for Accounts is widened from `*Repository` to every outbound port interface (`TenantRepositoryArchitectureTest.kt:26`), so the next such port must be classified.
**A system bind opens its own transaction.** Like the company aspect (M3), `bindSystemJob` opens a transaction when none is active. The audit dispatcher's `claimDue`, `markPublished` and `markFailed` run today as single statements outside any transaction (`AuditOutboxJdbcAdapter.kt:15-20`); with `SET LOCAL` each needs one.
`bindSystemJob` is allowlisted **by class**, not by package: the existing `SYSTEM_ALLOWLIST` admits the whole `ACCOUNTS_JDBC_ADAPTERS` package (`TenantRepositoryArchitectureTest.kt:449`), which would let all 76 adapters call it. A new arch rule names the system adapter classes (one per allowlisted system repository) and the job classes that may call `bindSystemJob`; any other caller fails the build.
**`audit_outbox` (D11):** the writer runs in the request's transaction, through the scope-first append port (M3). **The company policy on `audit_outbox` is `FOR INSERT` only, not `FOR ALL` (Fable, 2026-11-21):** `CREATE POLICY company_audit_insert ON accounts.audit_outbox FOR INSERT TO neoerp_accounts_app WITH CHECK (org_id = (SELECT neoerp_current_company()))`. A company request only ever inserts (`AuditOutboxJdbcAdapter.kt:26-48`, a plain `INSERT` with no `RETURNING`); `FOR ALL` would let any code under a company bind update or delete that company's pending audit rows before they are sent. The dispatcher reads and marks rows under system-job `SELECT` and `UPDATE` policies. Rows with a NULL `org_id` are read and marked only through the system policy. **One named exception (M7):** the Super Admin catalog-usage audit writes its own NULL-`org_id` row under the platform bind. **The domain-event outbox differs in one point:** the shared library inserts with `RETURNING id, company_id, occurred_at` and then fills the delivery rows from it (`shared/domain-events/src/main/kotlin/com/neovatus/events/producer/jdbc/JdbcOutboxStore.kt:33-45`), and Postgres checks a `RETURNING` row against the table's `SELECT` policy. So the company gets `FOR INSERT` on the event outbox and its delivery rows, plus `FOR SELECT` on the event outbox (or the library drops the `RETURNING`; the R2 brief decides), and no company `UPDATE` or `DELETE`; the feed reader and relay work under system-job policies. Event consumers already open a scope per event (ADR-019 D7).

**M7. Super Admin and platform-wide reads.** Enter-company sessions already get a normal `CompanyTenantScope` (`ServiceAuthorization.kt:91`), so they need nothing new. A `@PlatformWideRepository` adapter binds `neoerp.platform_access = <operationId>` from `PlatformTenantAccess`. A `FOR SELECT TO neoerp_accounts_app USING (neoerp_platform_access() IS NOT NULL)` policy exists only on the company tables that port reads: **today only `accounts_setups`** (Fable, 2026-11-21), which the chart-template and tax-pack usage counts read (`ACC/infrastructure/persistence/jdbc/PlatformCatalogJdbcAdapters.kt:102,126,137,166`); the template and tax-pack tables they join are reference tables with no RLS. No platform write policy exists (ADR-012 §3), with **one named exception: the platform-read audit row.** `PlatformCatalogUsageAudit` appends an `org_id = NULL` row to `audit_outbox` in the read's own transaction, then `complete()` rewrites its payload with the company count (`PlatformCatalogUsageAudit.kt:39-57,63-66`); the audit fails closed, so without a policy every usage read would be refused. The exception is insert-only: `CREATE POLICY platform_audit_insert ON accounts.audit_outbox FOR INSERT TO neoerp_accounts_app WITH CHECK (org_id IS NULL AND neoerp_platform_access() IS NOT NULL)`. **Recommended:** `complete()` appends a second row (same correlation id, `READ_USAGE_DONE`, the company count) instead of updating the first. A matching `FOR UPDATE` limited to `org_id IS NULL` was rejected: an `UPDATE … WHERE id = …` also needs a `SELECT` policy on those rows, which would let a platform bind read every other platform audit row. No other platform `INSERT`, `UPDATE` or `DELETE` exists. The arch test lets only the `PLATFORM_WIDE_ALLOWLIST` adapter classes call `bindPlatform`.

**M8. Not in scope now.** org, user and auth keep application checks, the 8-service arch test (Lane 0) and the L17 route tests. **audit-service is not left as "revisit later" (Fable, 2026-11-21):** it stores the same audit payloads Accounts protects under D11, with a nullable `org_id` and an optional filter (`services/audit-service/src/main/resources/db/migration/V1__audit_events.sql:4,11`; `AuditController.kt:26-30`), and HR/Payroll v2 will send salary and personnel changes there. It gets RLS on its company rows (`org_id`) in R7, with a dated go-live row; until then those rows sit behind application checks only.

**M9. What RLS does not stop (Fable, 2026-11-21).** The app role can call `set_config` itself, so this wall catches a missed or wrong company filter in our own code. It does not stop SQL injection or a taken-over service, which can set any company. Those stay with parameterised SQL, ADR-012 checks and the role separation of M5. This ADR adds one rule for the reporting store: it never runs SQL text supplied by a user. ADR-023 self-service builds its queries at run time, which is why it has RLS from day one (`NeoERP-BackEnd/docs/adr/ADR-023-reporting-layer.md:68`). If a customer's BI tool ever connected to the reporting database itself, a setting-based policy would not apply to it; R5 confirms BI goes through the API only.

## 5. Tests and acceptance
1. **Company A cannot read B:** for every company-bound table, a Testcontainers test as `neoerp_<svc>_app` binds A and counts B's rows = 0; insert or update with B's `company_id` fails. Generated from the catalog, so a new table is covered without new code.
2. **Missing setting denies:** in a fresh transaction with no bind, every company-bound table returns 0 rows; on a pooled connection that served A in the previous transaction, still 0 (the `''` case). **After a system-job or platform transaction**, a user transaction for A on the same connection (pool of 1) sees only A's rows in every queue, outbox, inbox, `accounts_setups` and catalog table, and cannot update or delete B's.
3. **No mixing:** binding B after A in one transaction throws; nothing commits.
3a. **REQUIRES_NEW:** an outer transaction bound to A calls an inner `REQUIRES_NEW` repository call for A; the inner call sees A's rows (set again on its own connection), and the outer call still sees A's rows afterwards. An inner call for B inside an outer A works on its own connection and leaves the outer at A.
4. **Pool:** 2 threads × 1 connection pool, alternating A and B 1,000 times, never see the other's rows.
4a. **Savepoint rollback:** an arch test finds no `NESTED` propagation or explicit savepoint in RLS services. A binder test binds A after a savepoint, rolls back to it, then reads: it sees A's rows (binder set it again) or 0 rows, never B's.
5. **Catalog check:** every table with a `company_id` column (and `audit_outbox` on `org_id`) has RLS enabled and forced and a `company_isolation` policy; every policy has a named role (none `TO PUBLIC`) and reads settings only through the M2 functions; system and platform policies exist only on the listed (table, command) pairs, which include `(audit_outbox, INSERT)` for the M7 platform-audit exception and no `(audit_outbox, UPDATE)` or `(audit_outbox, SELECT)` for the platform bind. An unlisted exception fails the build.
6. **Roles:** app role is not superuser, has no `BYPASSRLS`, owns nothing, cannot write reference tables (extends `DatabaseRoleTest`); owner without `neoerp.migration` sees 0 company rows.
7. **Jobs and platform:** system bind sees queue rows of A and B but 0 `journal_lines`; platform bind sees only the catalog tables; platform bind can append the start and completion NULL-`org_id` audit rows, and cannot read or write any company's `audit_outbox` rows (nor insert a row with a non-NULL `org_id`); the arch test rejects a call to either bind from any class not on its class allowlist (an ordinary JDBC adapter included).
8. These tests may not be skipped silently: the suite fails when Docker is missing (P-16, L18).
9. Measured: posting and GL report p95 on the ADR-024 large-tenant data differ by < 5 % with RLS on.

## 6. Consequences
Positive: a missed `company_id` in Accounts, Payroll, HR or reporting returns nothing instead of another company's data; native SQL and new report queries are covered; the posting-guard and runtime-role work is reused.
Negative: one more migration rule per table; a job or adapter that forgets its scope now fails (by design) and needs fixing; tests must run as the runtime role to mean anything; two small policy families (system, platform) to review.
Risks: a broad `neoerp.system_job` policy creeping onto business tables (the catalog test lists where it may exist); a policy reading a setting without `NULLIF` (the catalog test checks); `FORCE` on the owner read as a control against the owner, which it is not (M5); a hosted owner that is secretly a superuser (`RuntimeRoleCheck` and the go-live check); developers mistaking RLS for authorization (ADR-012 checks stay mandatory).
