# Step 1 Accounts — discovery for Jabran

**Status:** Discovery draft, 2026-10-05. Reading and this draft are approved; Accounts implementation, contracts, migrations and franchise fees are not. Recommendations below require Jabran’s decision and an owning implementation plan. The integration lead maintains `docs/agents/step0-followups/plan.md`; this is not a competing checkpoint.

**Evidence:** source rechecked at backend `3133db2` and App `d6b4248` after A–D delivery. Accounts service source is unchanged from initial backend `aea037a`, and the App Accounts feature source is unchanged from initial App `8f849a0`, verified by scoped Git diffs. No builds, service starts, live financial operations or runtime acceptance were performed for this discovery. Existing security code is an inventory, not certification that the ledger is ready for commerce.

## What exists

- Backend `accounts-service` owns fiscal years, accounting periods (open/closed/locked), chart of accounts and a template, cost centres, journals and GL/trial balance. Journal lines use `BigDecimal`; posting requires nonempty balanced lines, each line has a positive debit or credit, and reversal creates opposite lines and marks the original reversed. There are no implemented customer/invoice, supplier/bill, bank reconciliation, financial-statement, franchise-charge or consolidation use cases.
- `AccountsAuthorization` requires OAuth scope, effective IAM permission and FINANCE entitlement. Platform staff require a live Enter-company session, with READ_ONLY enforced by the lifecycle filter. Record actions derive the company from the record. These controls must survive Step 1; branch permission evaluation does not itself tag or isolate journal data by branch.
- App Accounts has the existing seven-area surface and a remote/repository layer. It has no Accounts screenshot fixture in the inspected tree. Backend test inventory contains `AccountsAuthorizationTest` and `AccountsActiveUserLifecycleFilterTest`, not ledger domain/service/report/template-copy regressions. No Accounts-specific App tests were found.
- Org already returns nullable `currency` and `fiscalYearStartMonth` in company data. Accounts currently has neither ledger currency nor a setup flow that consumes those values.
- HR owns employees; Payroll owns salary structures/components, periods, runs/items and payslips. No Accounts journal producer/client was found in their main source. `PAYROLL_RUN` appears as an illustrative source-type comment in Accounts V4; it is not an implemented posting integration.

## Current gaps to close before new finance features

| Gap and source | Minimum proposed correction / acceptance |
| --- | --- |
| App `AccountsRemoteDataSource` uses PUT for close/lock/activate/deactivate/post/reverse and updates. Backend controllers use POST actions and PATCH updates. | Agree the existing controller contract and align App; transport regressions cover each action and update. No gateway workaround. |
| App `AccountsRemoteDataSource.copyCoaTemplate` sends `targetCompanyId` only in a JSON body (lines 126–130); backend `ChartOfAccountController.copyTemplate` requires `@RequestParam targetCompanyId` (lines 59–63). | Align with the existing query-parameter contract. Transport regression must assert the query parameter and demonstrate populated template copy through the real controller; changing only the HTTP verb is insufficient. |
| Backend journals GET returns `{items,totalElements,page,size}` (`JournalDtos.kt` lines 57–61; controller lines 35–44). App `getJournalEntries` uses `decodeList`, which recognizes arrays/`content` but treats an `items` envelope as one DTO. All `JournalEntryDto` fields are nullable/defaulted and unknown keys are ignored, so `AccountsMapper.toJournalEntry` and the repository can produce one empty-id DRAFT row while the real journal items disappear. App also sends no page/size or follows the returned total. | Decode the actual `items` page envelope explicitly, preserve paging metadata and support the approved page-loading behavior. Reject malformed envelopes/invalid required journal fields instead of manufacturing a row or silently dropping items. Transport/repository regressions must use populated multi-page responses, assert real IDs/statuses/total/page/size and assert decoding failure for invalid shapes. |
| App GL actually calls `/api/accounts/gl`, not `/general-ledger` as the scope draft says. Backend serves `/api/accounts/reports/general-ledger`. App expects `GLReportDto` object; backend returns a list. TB path also lacks `/reports`, App expects `rows` while backend returns `lines`, and App can omit backend-required `periodId`. | Reconcile paths, required inputs and response shapes together; demonstrate populated real reports rather than accepting empty/default decoding. |
| `JournalEntryService.post` does not re-read the period after draft creation. A period can close before posting. Create checks period/account existence, but does not check their company against the command, cost-centre ownership, account active/leaf status or entry-date membership in the period. | Enforce current period and same-company related-record invariants transactionally; regressions for cross-company IDs, closed-between-create-and-post and concurrent close/post. Period/fiscal-year and COA-parent creation need the same ownership review. |
| `ChartOfAccountService.copyTemplate` generates new IDs but retains old parent IDs. It has no explicit repeat-copy policy or transaction annotation. | Remap the hierarchy and define safe repeated setup; database tests verify target-company parents, rollback and duplicate handling. |
| GL JPA query filters by journal entry date and POSTED status, but `ReportService` displays line creation date and null reference. It starts running balance at zero within the requested range. Queries exclude REVERSED originals even though reversal creates a POSTED opposite entry. | Specify entry dates/references, opening balance, stable ordering and how original/reversal pairs affect historical GL and TB. Test posted-only, pre-range opening, reversal and date/period boundaries. The existing status filter is not proof of accounting-correct reversal totals. |
| Period update lacks the creation date-order check; period creation does not validate the fiscal-year relationship/date range. | Specify overlap/date/fiscal-year rules and enforce both create and update. Test refusal without partial writes. |
| Accepted `standard-roles.md` D-R8 requires two-person journal posting even when a person holds both roles, with Owner as the audited exception. `JournalEntryService.post` delegates to `JournalEntry.post`, which checks draft state, nonempty lines and balance but never compares `actor` with `createdBy` or verifies/audits an Owner exception. | Preserve D-R8 and approve exact author/poster identity checks and the server-verified, audited Owner exception. Separate Write/Post permissions alone are insufficient. Add same-person refusal (including both roles), different-person success and Owner-exception audit regressions; a service check does not require a new approval engine. |
| No Accounts audit producer/outbox or business reason fields are present. | Use durable local outbox and machine publication like the accepted IAM/Org pattern; enumerate every mutation, mandatory final-action reason, actor/company attribution and nullable amendment/reference policy. Test rollback, retry and no event on refusal. |
| App money DTOs use `Double`, backend uses decimals; currency is absent. | Agree exact decimal transport/rounding and a company currency snapshot before financial UI or new documents. Do not silently choose currency when Org data is missing. |
| Journal lines have optional cost centre but no branch. | Add branch only through an approved contract/schema plan: verify company-owned branch, preserve separate franchise ledgers, test branch scope and reporting. |
| ADR-012 repository isolation is unfinished. The current tenant-scope baseline still lists Accounts repository methods, including ID-only reads/writes and a mixed template reference method. | Complete the applicable approved isolation gates before commerce, with company-bound ports, safe template separation and two-company negative tests. Controller authorization does not replace repository isolation. |

The scope draft’s broad problems remain useful, but its GL path wording, “franchise terms built in Step 0” heading and proposed fee posting must not be read as delivered contracts. Its draft D-A4 “Not in v1” recommendation conflicts with the accepted D-R8 two-person rule; preserve the accepted rule and reconcile that draft before a contract.

## HR, Payroll and franchise boundaries

Keep employee/pay calculation in HR/Payroll and financial posting in Accounts. Before a later Payroll integration, specify company-bound run identity, posting account mapping, approved run state, decimal totals, source uniqueness, retries and correction/reversal. A source-type string is insufficient for idempotent posting. Payroll’s ADR-012 compensating control must remain until its own exit criteria pass; Step 1 must not enable Payroll endpoints by implication.

`docs/drafts/franchise-terms-spec.md` is explicitly unapproved. Org relationship terms and Neovatus subscription agreements are distinct. Terms, a narrow franchisor view, date versioning and permissions are prerequisites for slice F, not existing capabilities. Accounts must not read other-company books using the human’s ordinary company scope. Any eventual machine operation needs explicit isolation, scoped authorization and durable evidence on both companies.

Two draft statements need resolution before a contract: “post both sides at once” cannot promise a distributed atomic transaction across separately owned company operations, and the FT migration sketches (`org V28`, `user V33`) are placeholders already used by other work. Reinventory numbers only when an approved migration is planned; preserve applied history. No fee contract or implementation is created here.

## Proposed slice order and gates

1. Reconcile the approved isolation prerequisite and Accounts contract inventory. Define negative tenant tests and preserve READ_ONLY/refusal behavior before commerce.
2. A1: fix App transport/report decoding and current ledger correctness (ownership, period timing, template hierarchy, report/reversal semantics), with domain/service and real persistence regressions. Acceptance includes the template-copy query parameter and populated journal pages with correct metadata/IDs/statuses, plus strict failures for malformed envelopes or missing required journal fields; no empty-id phantom rows or silent item loss.
3. A2: approved reason/audit contract and durable outbox, currency/fiscal-year first-run setup and branch tagging. Review migrations separately; render actual loading/error/empty/refusal states and verify personas through the gateway.
4. B: P&L, balance sheet and year-end close, after reconciled GL/TB totals.
5. C/D: receivables then payables with stable parties, decimal/tax rules and posting/reversal tests. E: bank/cash and manual reconciliation.
6. F only after separately approved Org franchise terms, receivable/payable foundations and scoped machine retry/compensation design. G last after approved group access, same-currency policy and elimination tests.

Each slice needs Discovery → Plan → independent review → approval before build, then tests, actual renders and interactive acceptance before delivery. This discovery establishes no Step 1 engineering completion, financial correctness certification or device acceptance.
