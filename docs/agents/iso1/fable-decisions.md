# ADR-026 row-level security: decision views

Reviewer: Fable 5.2 (high), decision views for Jabran
Reviewed: docs/drafts/ADR-026-row-level-security.md at 34913f93d76e7d3859e8a6fcc5d410819deaa7fd

Checked read-only against `NeoERP-BackEnd` on `phase/4` at d0dd5441. Paths below are under `NeoERP-BackEnd/` unless they start with `docs/`. `ACC` stands for `services/accounts-service/src/main/kotlin/com/neovatus/accounts`. The draft's own review files were not read.

## Summary

The direction is right and I agree with every recommendation in substance: option B, one company per transaction, a shared binder fed by the existing scope, narrow system and platform policies, tests as the runtime role. Nothing is a flat disagree. Eight of the eleven need a change before acceptance, and the changes share one cause: the draft counts 11 cross-company machine paths in Accounts, but the code has at least six more that the architecture test cannot see, and under the draft's rules they would not fail, they would quietly find nothing. The worst case is bank-key rotation reporting "0 remaining" while every company's old ciphertext is still there (`ACC/infrastructure/persistence/jdbc/BankDetailsReencryption.kt:85`). The other changes are smaller: audit-service keeps the same audit payloads with no second wall, the audit outbox policy should be insert-only for company requests, the hosted-only migration path is never tested locally, and no role is named for backups, the scheduled money checks or support access. The rollout order needs one change now that HR/Payroll starts in parallel: R1 plus database roles for hr-service and payroll-service must come first, and the first HR v2 migration should not wait for Accounts R2–R3.

## Open questions

- **Q1.** Answered, but see D9: "untouched" and "dropped" cannot both hold.
- **Q2.** Do not depend on what the provider's admin role can do. Flyway should run as a dedicated owner role per service created `NOSUPERUSER NOBYPASSRLS`, never as the provider admin; then the only provider question is "can we create such roles", which every managed Postgres allows. Provider snapshots are physical and unaffected by RLS; logical dumps need the backup role (missing item 4).
- **Q3.** Agree: no branch-level RLS. Branch and team visibility are permissions inside one company, not company isolation.
- **Q4.** Agree. I found no Accounts query over several companies for a person today; the only cross-company person read is the platform catalog usage count. Group consolidation (ADR-023 D13, `docs/adr/ADR-023-reporting-layer.md:129-131`) must be written as a loop per company when it is built.

## Rollout R0–R6 with HR/Payroll in parallel

The order no longer holds as "Accounts R1–R3, then R4". Recommended:

1. **R0.** Accept the ADR. The Lane 0 part is already merged (the 8-service ratchet is in `architecture-tests/.../TenantRepositoryArchitectureTest.kt:30-41`); the draft still describes it as coming and its line numbers into that file are stale.
2. **R1, now, ahead of everything.** It blocks the HR v2 build (PROJECT-STATE HRP-DES row). Widen it: the role script, `RuntimeRoleCheck` and the catalog test exist only for Accounts today (`infra/postgres/initdb/accounts-runtime-role.psql`, `ACC/infrastructure/persistence/jdbc/RuntimeRoleCheck.kt`); move them to shared code and add owner and app roles for hr-service and payroll-service. One lead owns the shared binder; the HR/Payroll stream only uses it.
3. **R4 may start after R1.** It does not need Accounts R2–R3. Its own gate: the HR v2 and Payroll v2 suites run as the runtime role from the first slice.
4. **R2 and R3 together**, as one merge (D8), after a written inventory of every SQL path that is not behind a tenant repository (missing item 2). This is the largest and riskiest step; it runs beside R4.
5. **R5** unchanged.
6. **R6** split: the provider check before the provider is chosen; the roles on the hosted stage before the pen test (D10).

The one real cost of running R4 before R2–R3: if Accounts shows the policy shape needs a change, HR v2's first migration is already applied and needs a follow-up migration. In dev that is cheap.

## Missing items a security reviewer would ask for

1. **Say what RLS does not stop.** The app role can call `set_config` itself, so this wall catches a missed company filter, not SQL injection or a taken-over service. State it in the ADR, and state that the reporting store never runs SQL text supplied by a user (ADR-023 builds queries at run time, `docs/adr/ADR-023-reporting-layer.md:68`).
2. **Cross-company paths the draft does not list.** The architecture test only sees interfaces named `*Repository` (`TenantRepositoryArchitectureTest.kt:21-27`). Outside it: `RecurringJobCompanies` (`ACC/application/port/outbound/recurring/RecurringJournalRepository.kt:238`; reads `recurring_journals` and two all-company gauges, `RecurringJournalJdbcAdapter.kt:623-643`), `ReversalScheduleCompanies` (`.../reversal/ReversalScheduleRepository.kt:82`), `ApprovalProposalQueue` (`.../approvallimits/ApprovalLimitPorts.kt:144`), `PayeeVerificationJobs` (`.../payables/PayeeVerificationProvider.kt:27`), and two classes with no port: `BankDetailsReencryption` and `BankKeyChecks`. Widen the test's name filter for Accounts and add each to the allowed (table, command) list or reshape it.
3. **"No rows" must not read as "all clear".** With no company set, re-encryption reports 0 remaining, the start-up key check passes without checking any ciphertext, and the alert gauges read 0. Recommended: on tables that have only the company policy, the flag function raises an error when no company is set, so a missed bind is an error and not an empty answer. Tables that also have a system or platform policy keep the NULL form. At minimum, R2 needs a test per scheduled job and start-up check, run as the runtime role with two companies, that asserts work was done in both.
4. **Named roles for operations.** None is defined for logical backup and restore, for the scheduled money checks in production (ERP-Q3; the script runs as the superuser today, `scripts/money-invariants.sh:29`), or for support access. Each needs a role no service holds, read-only where possible, with its use logged.
5. **A missing app role must fail the migration.** Today's migrations skip their grants when the role is absent (`V69__a4_journal_import.sql:130`). An RLS migration that skipped the same way would leave tables with no wall or with no policy. It must raise instead, and role creation becomes a step before Flyway on every stack and fixture.
6. **Start-up drift check.** `RuntimeRoleCheck` should compare the full set of policies against the expected list, not only the two table flags, so a hand-added permissive policy stops the service.
7. **Catalog test additions.** Every foreign key between two company tables carries `company_id` (228 of 270 in Accounts do; most of the rest point at reference tables); no `SECURITY DEFINER` function; raw `dataSource.connection` use in RLS services runs lock statements only (`LedgerCheckJdbcAdapter.kt:129`, `OrgSyncJdbcAdapters.kt:161`, `ExportJobJdbcAdapter.kt:313`).
8. **Direct BI access.** If a customer's BI tool ever connects to the reporting database itself, a setting-based policy does not apply to it. Confirm in R5 that BI goes through the API only.
9. **Rollback is not routine.** Turning RLS off in production removes ERP-Q4; make it Jabran's decision each time and an audited change, and write it as a forward migration.
