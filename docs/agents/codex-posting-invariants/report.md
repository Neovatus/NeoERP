## Findings

All findings are open; no implementation changes were authorized or made. High means financial-record integrity can be breached at the stated SQL boundary; Medium means workflow integrity, recoverability, availability, or an application concurrency guarantee is affected. Paper schedules below are not claims of executed reproduction.

### F-01 — High: transaction setting can authorize insertion into any old posted journal

**Failure scenario.** With ordinary INSERT access and a known posted journal/account, begin a transaction, execute `SELECT set_config('accounts.posting_journal_id', '<posted-id>', true)`, then insert a fresh line into that journal and commit. The trigger at M/V10__a1_journals.sql:313–315 checks only the setting's text. It never checks that this transaction originally posted the journal. The existing test at `PostedImmutabilityTriggerTest.kt:86–88` already performs the successful insert and rolls it back. This can append one side only, change line counts and break balance/report consistency. A line can also omit posting metadata because the line CHECK permits all-null metadata; K/infrastructure/persistence/jdbc/LedgerCheckJdbcAdapter.kt:47 excludes lines with null period_id, so that incomplete appended line escapes the nightly line-total comparison. Clearing the setting on pooled connections prevents leakage, not deliberate spoofing.

**Fix.** Make insertion authorization a database capability the DML role cannot forge: restricted posting function/privilege separation or protected transaction ownership tied to the header, with no ability to manufacture that ownership through ordinary writes. A caller-set GUC alone is insufficient. Add a committed-old-journal spoof test using the production-equivalent database role, and reject incomplete posted-line metadata.

### F-02 — Medium: invalid AR targets can deadlock two source credit notes

**Failure scenario.** Let A/B be two posted on-account credit notes with free balances. Request 1 allocates from A to B; request 2 allocates from B to A. K/application/service/receivables/allocation/AllocationService.kt:119 locks each source; :128 calls the general document-lock query on arbitrary target IDs, then filters invalid kinds in memory. K/infrastructure/persistence/jdbc/ArDocumentJdbcAdapter.kt:82 acquires the other credit note's UPDATE lock before validation. Both wait; one transaction is aborted. Expected result is a validation refusal without a source lock cycle; money remains transactionally safe but availability/error behavior does not.

**Fix.** Add/use an AR target-only query with debit invoice/opening predicates in SQL before FOR UPDATE, ordered by database UUID. Mirror K/infrastructure/persistence/jdbc/ApDocumentJdbcAdapter.kt:95–102. Test reciprocal invalid targets concurrently, expecting validation refusals and no deadlock.

### F-03 — Medium: direct SQL can rewind a numbering series and repeatedly wedge posting

**Failure scenario.** After legal numbers 1–10 exist, set the series' `next_value` to 1 using ordinary UPDATE. The schema checks positivity, not monotonicity. The next post takes 1; the legal-number unique index rejects it. Transaction rollback restores the counter to the same incorrect 1, so every retry fails. No duplicate committed legal number is created, but the series stops. Deletion/recreation of counter rows has a related reset risk. This is separate from credited line counters, protected by V28/V31.

**Fix.** Guard counter UPDATE against decreases and restrict counter-row deletion/reset to an explicit maintenance authority; test using the deployed application role. Preserve rollback semantics: rolling back an unissued number is legitimate and does not require an explicit decrement UPDATE.

### F-04 — Medium: expired approval-run lease permits duplicate bookkeeping

**Failure scenario.** Request A claims a batch and pauses after selecting SUBMITTED items. Its ten-minute lease expires. Same-user request B takes the run and selects overlapping items. Resume A. Source document locks and same-user approval replay prevent duplicate GL posting, but K/application/service/receivables/openingimport/ArOpeningImportSide.kt:136 discards replay status and each batch increments `posted`. Finalization at K/application/service/subledger/openingimport/OpeningItemImportService.kt:769–776 adds counters even when `mine == false`; :788 can enlarge `total` to fit. Two workers can report 400 posts for 200 actual documents. The live-claim and crashed-worker tests do not cover a stale live worker resuming.

**Fix.** Fence/renew worker claims and stop work after ownership loss; persist once-only per-run/item outcomes alongside approval or return/count first-approval outcomes durably. Do not blindly add stale-worker totals or count replays. Test a paused worker, expiry, successor takeover and original-worker resume.

### F-05 — High: SQL can mark a journal reversed without creating an inverse posting

**Failure scenario.** Post ordinary journals A/B. Execute `UPDATE accounts.journal_entries SET reversed_by_id = '<B>' WHERE id = '<A>'`. M/V10__a1_journals.sql:265–268 permits exactly this one-time change. The FK supplies existence/company integrity, not “B is RV and B.reversal_of_id=A with inverse lines.” The existing test `PostedImmutabilityTriggerTest.kt:43–46` uses another ordinary posted journal and expects success. A now appears reversed and future reversal is refused/replayed from the wrong link; no actual inverse accounting event was required. LedgerCheckJob compares amounts/aggregates, so this link-only tampering need not trigger its checks.

**Fix.** Enforce the reciprocal RV relationship at commit, preferably through a restricted atomic reversal operation plus deferred consistency constraints. Protect both sides against links manufactured through ordinary DML; test unrelated-JV links, wrong original/company, duplicate links and missing inverse posting.

### F-06 — Medium: the first-use control-account check is not serialized

**Failure scenario.** A company already has an unrelated committed posting, so setup locking is SHARE. No AR document is posted yet. A permitted manual control JV passes K/application/service/posting/PostingValidator.kt:405's existence check and locked recheck; pause before numbering. Another transaction posts the first AR document and commits. Both paths use compatible account SHARE locks (K/application/service/posting/PostingEngine.kt:1053), and independent journal series need not serialize them. Resume the manual JV: it commits after subledger use started without rechecking. The existing test only makes AR commit before the recheck. If the intended policy linearizes “use” at the earlier shared-lock validation rather than committed posting, this needs an explicit contract ruling; the current check does not enforce a commit-order cutoff.

**Fix.** Introduce a durable per-control-kind “subledger in use” transition serialized with manual-control admission, or acquire a common incompatible guard before both checks/first-use activation. Preserve the global lock order. Add a barrier test where first AR/AP use commits after manual validation but before the manual commit; decide the allowed ordering explicitly.

### F-07 — High: nonlocking parent-status check allows AR line mutation during approval

**Failure scenario.** An approver locks a SUBMITTED invoice header at K/application/service/receivables/document/ArDocumentApprovalService.kt:112, reads its lines at :125 and prepares the posting at :133. A second SQL connection changes an ordinary non-key line field (for example description, or matching net/net_base amounts within line CHECK constraints). The current V28 trigger at M/V28__sb3_receivables_guards.sql:23–27 reads the parent with a plain SELECT. Under READ COMMITTED it sees the committed SUBMITTED status while approval's header is locked or being updated, so :53's posted-content prohibition does not apply. A non-key child UPDATE does not acquire the parent's UPDATE lock. Approval writes tax rows but does not lock/rewrite ordinary line rows (K/infrastructure/persistence/jdbc/ArDocumentJdbcAdapter.kt:131–148), then marks the header posted at :151–162. The journal/header can commit using old lines while the stored posted line contains the concurrent edit. The SQL transaction can also hold its edited line until after approval commits, making the altered content visible after posting.

This is not the API creator-edit race, which takes the parent lock correctly. It is a database-trigger gap when another ordinary DML path fails to follow the service lock protocol. Sequential posted-line tampering tests do not cover it.

**Fix.** Serialize child mutation with parent status transitions using a consistent parent-before-child locking protocol enforced for all permitted writers, and validate the final children before the POSTED transition. Adding locks inside row triggers needs deadlock analysis because the child tuple may already be locked. Add a two-connection regression with approval paused after reading children, direct SQL child mutation and both commit orders.
