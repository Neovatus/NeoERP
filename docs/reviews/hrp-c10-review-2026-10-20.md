## 2. Reporting model (P4-A9 to A14) — FAIL

### What passes

- **Families and recipients.**
  - Profiles are predefined per country (`PAY_C_PROFILES`).
  - IS has separate tax, fund and union families, and FI has separate earnings and employer families.
  - An unknown recipient is refused with `FILING_RECIPIENT_PROFILE_MISSING`.
  - Unregistered body fields are refused with `VALIDATION`.
- **PAYMENT reports.**
  - The period key is `payDate:eventId`, so there is one report per PAID event.
  - PLANNED events, events dated in the future and events in another month all give `PAYMENT_NOT_FINAL`.
  - The deadline is a nominal 5 days after payment, labelled UNCHECKED.
- **FACTS_ONLY reports.**
  - There is no payment event, run or line: the registry is frozen and no code path writes a payment.
  - `totals` is null, `sourceEventIds` is empty, and the records have no money keys.
  - With `fact_basis = NONE`, a facts-only source gives `FILING_NOTHING_TO_FILE`.
  - CANCEL also has `records = []` and null totals.
- **Correction models.**
  - REPLACE_WHOLE sends the full record set.
  - CORRECT_PERIOD:
    - only affected keys are sent;
    - a PARTIAL outcome limits the keys to the rejected ones;
    - the cutoff is applied, with `route: EXTERNAL`;
    - fields that are final after the first submission give `FIELD_FINAL_AFTER_FIRST_SUBMIT`.
  - CANCEL_AND_NEW:
    - CANCEL carries references only;
    - NEW_AFTER_CANCEL needs the CANCEL version to have ACCEPTED or RECEIVED evidence, and gets a new `reportRef`.
  - Versions are frozen and keep their parent and lineage root. Earlier bytes and hashes are unchanged.
- **Evidence.**
  - Upload records a TRANSMISSION with `outcome: null`, which shows as UPLOADED. Upload alone never accepts.
  - Feedback:
    - must be correlated by family, recipient, period, reference, hash and issuer;
    - needs a message ID and `receivedAt`, plus a CLEAN file or an explanation;
    - PARTIAL needs record-keyed diagnostics;
    - the same message ID with the same content replays, and with different content gives `FEEDBACK_CONFLICT`;
    - a later message supersedes an earlier one.
- **Labels.** Every file carries "Sample — not an official format", and every terminal outcome shows "Synthetic feedback evidence".

### Findings

**C10-1 Medium — correction lineage can branch, so a report can be duplicated**

- **Where:** `payroll-data.jsx:3087` (the parent is any version, found by ID) and `:3094`.
- **Problem:** nothing requires the parent to be the head of its lineage, and nothing refuses a second child of the same parent. As a result:
  - two NEW_AFTER_CANCEL versions can be made from one CANCEL, each with a new `reportRef`, so the same payment is reported twice;
  - two CANCELs or REPLACEs can be made off one original.
- **Conflicts with:**
  - P4-A12, which requires immutable linear lineage;
  - the §9.2 single `correctionPending` state.
- **Fix:**
  - Refuse a correction unless its parent is the current lineage head that has no child (`CORRECTION_ACTION_NOT_ALLOWED`).
  - State the head-only rule explicitly in P4 §2b.4.

**C10-2 Low — `cancelOnly` and CANCELLED are not modelled**

- **Where:** `payroll-data.jsx:3078` and onwards.
- **Problem:** P4-A12 has `cancelOnly: true` ending the lineage, with a derived filing status of CANCELLED. The rig has neither.
- **Fix:** add a `cancelOnly` flag that ends the lineage and shows CANCELLED.

**C10-3 Low — upload reuses the wrong error code**

- **Where:** `payroll-data.jsx:3123`.
- **Problem:** a missing manual-transmission reference returns `ORIGINAL_REFERENCE_REQUIRED`. In P4-A12 that code means a target was filed outside NeoERP without a recorded reference.
- **Fix:** use `VALIDATION` with field `reference`, or a dedicated `REFERENCE_REQUIRED`.

## 3. Country specifics — PASS

The rig, P5 to P9 and the drafts are consistent with each other:

- **NO:** EMPLOYMENT_ACTIVE, MIXED months and REPLACE_WHOLE of one message in the same month.
- **SE:** CORRECT_PERIOD. Absence facts go only on the first original, and absence is final after the first submission.
- **DK:** CORRECT_PERIOD with the 15 February candidate cutoff, marked UNCHECKED.
- **FI:**
  - PAYMENT earnings and MONTH employer/no-wages reports, both CANCEL_AND_NEW.
  - A monthly renewal cannot cross periods: `:3089` allows a period change only for NEW_AFTER_CANCEL on PAYMENT kinds.
- **IS:**
  - Tax, fund and union lineages are independent.
  - REPLACE_WHOLE is labelled as a synthetic demo mode only (`correctionModeCheckState: UNCHECKED`).

P5 to P9 add no table, endpoint, DTO or state machine. Local P5-A1/A2, P8-A2/A3, P9-A4 and `DK_EINDKOMST_PRIOR_YEAR_TAX_CUTOFF` are marked as superseded by P4 §2b.

**C10-4 Low — DK cutoff is broader than P7 allows**

- **Where:** `payroll-data.jsx:3097`.
- **Problem:** the DK cutoff blocks every correction. P7 (`p7.md:272-275`) limits it to A-skat and AM fields: "no broader cutoff is inferred".
- **Fix:** apply `CORRECTION_CUTOFF_PASSED` only when the changed fields include the A-tax or AM groups.

## 4. Permissions and privacy — PASS

- **`payCGate` (`:3068`):**
  - Platform actors, other companies and unknown companies are refused with `FORBIDDEN`.
  - The `read` mode, which serves summaries, needs only `FILING.READ` or `FILING.VIEW`.
  - The `content` mode needs exact `FILING.CONTENT.READ`.
  - Generate and submit need their own code plus `CONTENT.READ`.
  - Offline and service-unavailable states are checked.
- **Summaries:** the public version carries totals, state and counts only. Content reads are audited (`CONTENT_READ`).
- **Evidence files:** PENDING files are visible to their uploader only, and REJECTED file metadata is dropped.
- **Personas:** the accountant has `FILING.READ` only. Only the owner and admin personas get `FILING.CONTENT.READ`.
- **No persistence:**
  - No uploaded bytes are read or kept; the rig stores metadata only.
  - State is in memory, with no store writes.
  - The legacy `payNordic*` helpers now delegate to the gated model, so the old feedback path cannot bypass it.
